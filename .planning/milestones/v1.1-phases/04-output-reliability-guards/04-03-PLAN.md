    Change 3 — add `@patch("cli.run_guards")` decorator and corresponding `mock_guards` parameter
    to each test method that exercises the success path (i.e., each test where
    mock_generate.return_value is set, meaning run_guards would be reached). For each such test:
    - Add `@patch("cli.run_guards")` as the innermost patch decorator (outermost in parameter order,
      so it becomes the first positional parameter after `self`)
    - Add `mock_guards` as the first parameter after `self` in the method signature

    Decorator order rule for unittest.mock.patch: decorators apply bottom-up, parameters map
    bottom-up to top-down. The existing decorator stack for test_end_sentinel_breaks_loop is:
      @patch("sys.argv")
      @patch("cli.write_resume")
      @patch("cli.generate_tailored_resume")
      @patch("cli.read_resume")
      @patch("builtins.input")
      def test_...(self, mock_input, mock_read, mock_generate, mock_write, ...):
    Add `@patch("cli.run_guards")` between `@patch("cli.generate_tailored_resume")` and
    `@patch("cli.read_resume")`, which means `mock_guards` appears between `mock_generate`
    and `mock_read` in the parameter list — OR place it as the outermost decorator and add
    `mock_guards` as the last positional parameter. Either is correct; choose the approach that
    is clearest for the test reader. The simplest: add `@patch("cli.run_guards")` immediately
    above the `def test_...` line (making it the innermost decorator = last parameter).

    Tests with side_effect = RuntimeError do NOT reach run_guards and do NOT need the patch.
    The test_empty_jd_exits_1 test also does NOT need the patch (no mock_generate at all).
